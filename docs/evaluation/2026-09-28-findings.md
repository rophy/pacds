# PACDS evaluation findings (2026-09-28)

Continues `2026-09-27-findings.md` with the Debezium case set and the support agent. LLM: `gpt-6-luna`
(OpenCode Go, Responses API) for PACDS, the no-code baseline and the support agent. Baseline = same model, same
question, report and logs only, no code.

The runs before 2026-09-28T14:30 were not traced or archived: these numbers are their only record. Later runs
are archived in S3 (`python -m tests.eval_run list`).

## 1. Test bed

- **Debezium candidates** (`tests/replay/candidates/debezium-*/`, rophy/pacds#1): 121 fixtures from the Debezium
  Google Group, plus 7 rejected (`rejected.json`). Run with `--candidates`.
- **Catalog**: `tests/replay/CATALOG.md`, generated by `python -m tests.replay.catalog [--check] [--after DATE]`:
  source, date, set, class, review tier, baseline p(truth), per-model training-cutoff marks.
- **Labels**: the 51 candidates the baseline gets wrong were reviewed twice, blind (`reviews` in `case.json`):
  tier `certain` 18, `probable` 33; classes A 1, B 31, C 13, D 6. The other 70 are `unreviewed` (the baseline
  gets them right).
- **Caveat**: Debezium group reporters operate everything themselves, so B (user error) and C (infrastructure) are
  inherently blurry.

## 3. Miss analysis (hand-classified from transcripts, run 08:44)

- **D misses (18)**: `pacds_wrong` 8 (PACDS confidently denied regressions: the code looked deliberate and it had
  no history then), `wrong_questions` 5, `agent_overrode` 3, `defensible` 2.
- **C misses (30)**: `wrong_questions` 13 (the agent never asked *who controls the failing setting*: DB grants,
  publications, topic config, platform classpath), `agent_overrode` 8, `no_pacds` 5, `pacds_wrong` 2,
  `defensible` 2.

These led to the playbook changes (classify by where the fix is made; boundary rules; regression step; "whose
fix is it" step) and to PACDS's `git_log`/`git_show` tools.

## 4. Cost

A full run (51 × 3, both variants) is about 30M input tokens, 27M of them PACDS (208 investigations, average 130K
input, median 6 turns). An estimated 79% of PACDS input is earlier tool results resent every turn
(`search_code` and `read_file` dominate).

The first traced run (`20260928T-phase1-check`, 8 PACDS requests) shows OpenCode Go already caches about 67% of
PACDS input tokens. The resend share therefore overstates the cost by however much cached tokens are discounted;
the phase 2 cost report should measure it from traces.

The phase 2 report on that run splits it further (3 cases, so indicative only): about 82–84% of PACDS input is
history resent from earlier calls, 60–74% of it tool results (`search_code` and `read_file` about 35–40% each).
Investigation calls are about 80% cached, but the **final-answer calls get no cache hits** (0 of 194K tokens):
the final request drops the tools and adds a response format, which probably breaks the cached prefix. That is
about 15% of PACDS input at full price, and a candidate for the token-reduction work.

## 5. Traced milestone (2026-09-28)

Current PACDS (git history) and playbook, 51 reviewed cases × 3 repeats, gpt-6-luna. Three runs of one repeat each
(`20260928T153348Z`, `20260928T160034Z` plus `20260928T212843Z-part2-rerun` for the 43 tickets the weekly usage limit
failed, `20260928T214915Z`); merged report in `eval-runs/milestone-20260928/` (not archived as such: rebuild it with
`python -m tests.analysis report RUN1 RUN2 RERUN RUN3 --out DIR` after fetching the four runs). No infrastructure
failures remain.

| | all (153) | B (93) | C (39) | D (18) | A (3) | cases right ≥2/3 | escalation |
|---|---|---|---|---|---|---|---|
| baseline (no code) | 21% (15–28%) | 28% | 8% | 11% | 33% | 11/51 | - |
| support agent without PACDS | 36% (29–44%) | 46% | 23% | 17% | 0% | 19/51 | 69% |

Paired by case (majority of 3): with PACDS vs the no-code baseline 18 cases gained, 4 lost, **McNemar p = 0.004**;
with vs without PACDS 10 gained, 4 lost, **p = 0.18** — a consistent gain (+16 points over 153 tickets), not yet
significant at 51 cases. Compared with the run of 2026-09-28T08:44 (before git history): 47% → 52% with PACDS; C
23% → 38%; **D unchanged** (11% → 17%, 3 of 18).

Cost: the with-PACDS variant is 44.3M input tokens (73% cached) and 1.0M output for 153 tickets, about **$2.00** at
OpenCode's list prices (baseline and no-PACDS $0.10 each). PACDS: 242 investigations, median 9 turns, 6 files, 95%
used git history; 85% of its input is history resent from earlier calls (76% tool results); 2 ran out of turns. The
agent sent 12 invalid PACDS requests (422), which count as its behavior, not failures.

**Failure modes of the 73 with-PACDS misses** (`classify`, gpt-6-luna; agrees with a hand classification of part 1's
24 misses on 21, see `2026-09-28-hand-classification.json`):

| truth | pacds_wrong | pacds_wrong_evidence | wrong_questions | agent_overrode |
|---|---|---|---|---|
| B (32) | 11 | 4 | 8 | 9 |
| C (24) | 0 | 6 | 15 | 3 |
| D (15) | 14 | 0 | 0 | 1 |
| A (2) | 0 | 0 | 0 | 2 |

What this says:
- **D misses are PACDS's**: 14 of 15 are PACDS answering the regression/defect question wrong while reading the
  relevant code — it denies regressions even with the history tools (it used them in 95% of investigations).
- **C misses are the agent's questions**: 15 of 24 never asked the deciding question (who controls the setting:
  grants, publications, Schema Registry, WAL retention); 6 more are PACDS reading the wrong code.
- **B misses are mixed**, including 9 where PACDS pointed to the truth and the agent decided otherwise.
- The agent asks whether a behavior is deliberate in 148 of 153 tickets; asking it does not help (51% right when
  asked vs 80% in the few tickets that did not), which fits PACDS over-reading "deliberate" code as intended.

**Replay** (phase 3): replaying part 1 served all 1,078 calls from the recording and reproduced every decision;
changing the final-answer instruction re-ran only the 3 final calls of 3 recorded investigations. Recorded
failures are replayed as failures; a call cancelled by the time budget cannot be and goes live.

## 6. Providers

- **OpenCode Go** (`gpt-6-luna`, training cutoff 2026-05-18, Responses API, header `x-opencode-session`): works;
  it has a 5-hour usage window **and a weekly limit** (hit 2026-09-28 after about 20M tokens that day). A full
  milestone (about 45M tokens) does not fit in one week together with development runs. A 429 names the limit in
  `metadata.limitName`, and `Retry-After` gives the seconds until it resets.
- **Plugsky** (`https://plugsky.com/v1`, chat completions, credential injected by the proxy): the account is on a
  trial plan capped at `plugsky-plus`. `plugsky-plus`/`-pro` are Nemotron 3 Nano Omni 30B-A3B (reasoning);
  `plugsky-max` is Nemotron 3 Ultra 550B. Fallback models are silent; responses report only the tier name. Needs
  `LLM_MAX_OUTPUT_TOKENS=16000` (otherwise "final answer did not complete: length"); about 12% of JSON-format
  calls return 502 (now retried). First pilot (before those fixes, concurrency 4): baseline 87/153 failed, 9/66
  right. Run it with, e.g.
  `env LLM_BASE_URL=https://plugsky.com/v1 LLM_MODEL=plugsky-plus LLM_API= LLM_SESSION_HEADER= LLM_API_KEY=x LLM_MAX_OUTPUT_TOKENS=16000 ./scripts/eval.sh ...`
