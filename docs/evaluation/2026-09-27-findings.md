# PACDS evaluation findings (2026-09-27)

Status of the evaluation phase: does PACDS help a support team decide whether a ticket must go to the
development team, and what did we learn building the evaluation?

LLM: `gpt-6-luna` (OpenCode Go, Responses API) for PACDS, the no-code baseline and the support agent.
All numbers come from runs in the Kind dev cluster; most are 1–3 runs, so single-case differences
are within noise.

## 1. Test bed

- **Cases** (`tests/replay/cases/`): 23 real, closed GitHub issues from go-gitea/gitea,
  louislam/uptime-kuma, usememos/memos and linkwarden/linkwarden. Each is replayed against the code as
  it was (the reported version tag, or the parent of the fix commit for bugs), with the logs the
  reporter pasted served from MinIO through presigned URLs.
- **Classes** (the support team's taxonomy): A other system, B user error, C infrastructure, D bug.
- **Ground truth** = the development team's conclusion (maintainer verdict plus reporter confirmation
  or a merged fix), confirmed by two independent blind reviewers. Each case records the reviews.
- **Sets**:
  - `clear` (12, 3 per class): the report and logs largely decide the class.
  - `hard` (11): cases the no-code baseline gets wrong or is unsure about (p(truth) ≤ 0.6); the report
    looks like one class but the code shows another. Tier `certain` (6) = both reviewers certain;
    `probable` (5) = at least one reviewer only probable.

## 2. Results

### Fixed-question replay (`tests/replay/harness.py`)

One hand-written question with the four classes as options.

| Configuration | Clear | Hard |
|---|---|---|
| No-code baseline (report + logs, no code, one LLM call) | 36/36 | 9/33 (27%) |
| PACDS, first hard-set run | — | 11/18 on the first 6 hard cases |
| PACDS + "check intent before blaming the code" (server prompt) | 36/36 | 24/33 |
| PACDS + "symptom the code cannot produce comes from outside" (server prompt) | 35/36 | 28/33 (85%) |
| PACDS, general server prompt; taxonomy moved to the client's options | 36/36 | 25/33 |
| PACDS, general prompt + client options split A/C by "who controls the cause" | — | 24/33 (C cases 12/12) |

### Support agent (`tests/support_agent/`)

An air-gapped support agent (knows the application name, report and logs; no repository or version)
with two skills — `tech-support` (the ABCD playbook, tool-agnostic) and `pacds` (general usage guide) —
and one tool, `call_pacds`, whose code version is bound to the deployment. One run each:

| Variant | Clear | Hard | Escalation accuracy | PACDS calls / ticket |
|---|---|---|---|---|
| Support agent + PACDS | 12/12 | 8/11 (73%) | 87% | 0.7 clear, 1.7 hard |
| Support agent, no PACDS | 12/12 | 6/11 (55%) | 78% | — |

## 3. Findings

1. **Code access pays off only on hard cases.** On clear cases a model answers from the report and
   logs alone (100%) at ~1/40 of the tokens. On hard cases, reading the code moves accuracy from 27%
   to 73–85%. A cheaper design to consider later: answer from report and logs first, investigate the
   code only when that answer is uncertain.
2. **The model's default is "bug".** Without evidence it calls surprising behavior a defect (almost all
   no-code misses were D). The winning investigation habit is to find the code that produces the
   behavior and decide whether it is deliberate or accidental.
3. **Remaining PACDS misses are judgment, not search.** Tool-call traces show the agent reads the
   deciding code in its misses; it draws the wrong conclusion. Hardest: negative inference (gitea-30748
   — correct only when the agent concludes "the code handles this, so something in front of the app
   changed the request"; 0/3 before the negative-inference prompt, 6/10 after it, 3/3 with the A/C-split
   client options; the support agent missed it).
4. **Answer quality depends on the client's question.** With a general server prompt, rewording only
   the client's options moved hard C cases from 9/12 to 12/12. Overlapping options (A and C with the
   same hint) cost accuracy. Hence the split of responsibilities below.
5. **An agent can drive PACDS from a skill file.** The support agent turned the playbook into narrow,
   code-checkable PACDS questions (e.g. "is this deliberate?", "under what condition is msg
   recorded?") and matched the hand-tuned question on hard cases (73%). It used PACDS where it mattered
   (0.7 calls/ticket on clear, 1.7 on hard) and gained over its no-PACDS self (73% vs 55%).
6. **Ground truth needs care.** Of the first 12 candidate cases, several were debatable on review;
   "surprising but intended" behavior (B vs D) and "who controls the cause" (A vs C) are where labels
   and models disagree.

## 4. Design decisions taken

- **PACDS is a general question-answering service.** The server prompt only says how to investigate
  (deliberate vs accidental, where an error originates, what the code cannot produce) plus the leak
  guardrails. Taxonomies such as ABCD belong to the client.
- **Clients own question quality**: mutually exclusive options separated by a concrete test (README
  "Writing good questions"; `tests/support_agent/skills/pacds/SKILL.md`).
- **Evaluate one layer at a time**: fixed client wording when comparing PACDS versions; fixed PACDS
  when tuning client wording.

## 5. Bugs found by the evaluation (fixed)

- LLM 429 with a long `Retry-After` (quota reset in hours) hung requests → capped, fails fast with 529.
- The TypeSafe adapter's prompt ("use only the supplied document") made models skip investigation, and
  questions reached the model only at the final answer → replaced; questions shown from turn 1.
- Some models (OpenAI GPT on OpenCode Go) only work on the Responses API → `llm.api: responses`.
- `httpx` logged full presigned log URLs, leaking the signature into pod logs → query strings stripped.
- `mc pipe` buffered 528 MiB parts and OOM-killed MinIO during seeding → `--part-size 5MiB`.
- A single LLM call timeout was reported as "time budget exhausted" (504) without retry → retried, 529.
